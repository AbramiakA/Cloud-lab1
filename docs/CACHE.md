# Кешування операцій читання

## Налаштування кешу

Для кешування використано Redis OSS 7.1 через Amazon ElastiCache. Він працює як спільний кеш для всіх ECS Tasks.

Кешування додано до `GET /api/products/{id}`, оскільки цей запит виконується найчастіше в нашому сценарії навантаження.

Використано схему cache-aside: спочатку товар шукається в Redis, а якщо його немає — читається з MySQL і зберігається в кеші на 30 секунд.

Після оновлення або видалення товару відповідний запис у Redis очищується. Якщо Redis недоступний, застосунок продовжує працювати через MySQL.

## Порівняння результатів

Проведено два тести k6 з однаковими параметрами: 100 VU, 3 хв наростання, 5 хв сталого навантаження та 2 хв спаду.

| Показник | Без кешу | З кешем |
|---|---:|---:|
| Кількість запитів | 76 690 | 94 280 |
| RPS | 127,60 | 157,13 |
| p95 | 1,10 с | 1,28 с |
| Помилки | 0% | 0% |
| CPU RDS | 8,93% | 7,21% |

Із увімкненим Redis отримано 65 526 Cache HIT та 9 898 Cache MISS. Частка влучань у кеш становила **86,87%**.

З увімкненим кешем пропускна здатність (RPS) зросла приблизно на 23%, а навантаження на MySQL зменшилося. Водночас p95 збільшився з 1,10 до 1,28 с, тому кешування покращило не всі показники.

## Актуальність даних

Оскільки TTL становить 30 секунд, без очищення кешу клієнт може бачити застарілі дані до 30 секунд.

Щоб зменшити цей час, після оновлення або видалення товару відповідний запис видаляється з Redis. Також за потреби можна зменшити TTL.
